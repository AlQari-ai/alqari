# Arabic Document Intelligence Benchmark Methodology

*A reproducible framework for evaluating Arabic OCR, handwriting recognition, document understanding, structured extraction, and processing latency.*

---

## Purpose

Comparing document intelligence systems fairly is difficult. Numbers quoted without context — a single "accuracy" percentage, a vendor-reported latency figure — are rarely comparable across systems. A result is only meaningful when every system is measured under the same conditions.

A fair comparison requires:

- the **same documents** for every system under test
- the **same ground truth** reference
- the **same preprocessing policy** (how images are handled before recognition)
- **task-appropriate metrics** (character-level, word-level, field-level, layout)
- **versioned models and configuration** recorded with every run
- **reproducible evaluation conditions** that another party can repeat

This document is a **methodology**, not a results publication. It defines *how* ALQari evaluates Arabic document intelligence so that any reported numbers can be reproduced and audited.

### Capability comparison vs performance benchmark

These are two different things, and this repository keeps them separate:

| | Capability comparison | Performance benchmark |
|---|---|---|
| **Question answered** | Does the system support a capability? | How well does the system perform the task, quantitatively? |
| **Evidence** | Public documentation, product behavior | Measured scores on shared data |
| **Output** | Supported / configuration required / not documented | CER, WER, F1, latency, etc. |
| **Where published** | [alqari.sa/benchmark](https://alqari.sa/benchmark) | Follows this methodology (not yet published) |

A lack of public documentation is **not** evidence that a capability is absent. Capability comparison and measured benchmarking must never be conflated.

## Document Categories

Document intelligence performance varies enormously by document type. A single blended score hides this. Evaluation is therefore organized into distinct categories, each scored independently:

1. **Arabic printed documents** — typeset or printed Arabic text.
2. **Arabic handwritten documents** — handwritten Arabic, including forms and free text.
3. **Mixed Arabic / English documents** — bidirectional text with Latin tokens.
4. **Invoices and forms** — semi-structured business documents.
5. **Degraded / scanned documents** — low-resolution scans, skew, noise, photocopies.
6. **Structured field extraction** — extracting named fields rather than raw text.
7. **Layout / table understanding** — reading order, regions, and table structure.

Category boundaries should be documented for each run. Dataset sizes are not asserted here; each published benchmark must state the exact number of documents and pages it used (see the [Reporting Template](#reporting-template)).

## Ground Truth

Scores are only as trustworthy as the reference they are measured against. Recommended practices for preparing ground truth:

- **Human-verified transcription** — text references are transcribed and checked by a person, not generated by another OCR system.
- **Field-level reference values** — for extraction tasks, record the expected value of each field (e.g., `invoice_number`, `total_amount`).
- **Layout annotations where applicable** — region boundaries, reading order, and table structure for layout tasks.
- **Consistent normalization policy** — the same normalization is applied to both prediction and reference (see [Arabic Normalization Policy](#arabic-normalization-policy)).
- **Double review for ambiguous handwriting where practical** — difficult handwritten samples are reviewed by more than one annotator to reduce reference error.

This section describes the methodology for preparing ground truth. It does not assert that any specific annotation team or process is currently in use; each published benchmark should disclose how its ground truth was produced.

## Arabic Normalization Policy

**CER and WER depend heavily on normalization.** The same prediction can score very differently depending on whether Alef variants, diacritics, or digit forms are normalized before comparison. For this reason, a benchmark must **document its normalization policy explicitly** — silent normalization invalidates comparison.

Report **both** a **raw score** (no normalization beyond Unicode form) and a **normalized score** (policy applied), because each answers a different question: raw reflects exact transcription fidelity; normalized reflects semantic/textual equivalence.

Recommended policies to document for each benchmark:

| Feature | Example | Recommended decision to document |
|---|---|---|
| **Alef variants** | أ إ آ ا | Whether hamzated Alef is folded to bare Alef (ا) |
| **Ya / Alef Maqsura** | ي ى | Whether final Ya and Alef Maqsura are unified |
| **Ta Marbuta** | ة ه | Whether Ta Marbuta is folded to Ha |
| **Diacritics (tashkeel)** | َ ً ُ ٌ ِ ٍ ّ ْ | Whether harakat are stripped before scoring |
| **Tatweel (kashida)** | ـ | Whether elongation characters are removed |
| **Punctuation** | ، ؛ ؟ . , | Whether punctuation is kept, stripped, or mapped |
| **Arabic / Latin digits** | ٠١٢٣ vs 0123 | Whether digit scripts are unified before scoring |
| **Whitespace** | multiple/trailing spaces | Collapse runs, trim edges |
| **Unicode normalization** | NFC / NFKC | Which normalization form is applied first |

State the exact policy (feature-by-feature) alongside every reported number. Two systems can only be compared when they were scored under the **identical** policy.

## CER — Character Error Rate

Character Error Rate measures recognition quality at the character level using edit distance:

```
CER = (S + D + I) / N
```

where **S** = substitutions, **D** = deletions, **I** = insertions (the Levenshtein edits transforming the prediction into the reference), and **N** = number of characters in the reference.

CER is well suited to Arabic OCR and handwriting because Arabic is cursive and context-sensitive: characters change shape by position, letters connect, and diacritics add fine detail. Character-level scoring captures partial correctness that word-level scoring would discard.

### Illustrative example (illustrative only — not a measured result)

- Reference: `كتاب` (4 characters)
- Prediction: `كتب` (the Alef is dropped)

One deletion, so `CER = (0 + 1 + 0) / 4 = 0.25` (25%).

---

## WER — Word Error Rate

Word Error Rate applies the same edit-distance idea at the word (token) level:

```
WER = (S + D + I) / N
```

where S, D, I are word-level edits and **N** is the number of words in the reference.

WER is sensitive to decisions that CER is not:

- **Tokenization** — how the text is split into words must be identical for prediction and reference.
- **Punctuation policy** — whether punctuation is a token, attached to a word, or removed.
- **Arabic word boundaries** — clitics and attached particles (e.g., prepositions, conjunctions) affect what counts as a "word".
- **Mixed Arabic / English documents** — bidirectional text and Latin tokens require a tokenization rule that treats both scripts consistently.

### Illustrative example (illustrative only — not a measured result)

- Reference: `إجمالي الفاتورة 100 ريال` (4 words)
- Prediction: `إجمالي الفاتورة 100 ريالا` (last word substituted)

One substitution, so `WER = (1 + 0 + 0) / 4 = 0.25` (25%).

## Structured Extraction Metrics

OCR quality alone does not tell you whether the **right data** was extracted. A document can have excellent CER yet the wrong invoice total. Structured extraction is therefore scored on the extracted fields, not the raw text.

Recommended metrics:

- **Exact Match** — the predicted field value equals the reference exactly.
- **Normalized Exact Match** — equality after a documented normalization (e.g., date format, digit script, whitespace).
- **Precision** — of the fields the system returned, how many were correct.
- **Recall** — of the fields that should have been returned, how many were found.
- **F1** — the harmonic mean of precision and recall.
- **Field-level accuracy** — per-field correctness, reported individually where appropriate.

Report per-field so that strengths and weaknesses are visible rather than averaged away. Typical invoice fields:

| Field | Example reference | Suitable metric |
|---|---|---|
| `invoice_number` | `INV-2024-0481` | Exact / Normalized Exact Match |
| `supplier` | `مؤسسة النور التجارية` | Normalized Exact Match, F1 |
| `date` | `2024-09-28` | Normalized Exact Match |
| `vat` | `900.00` | Normalized Exact Match (numeric) |
| `total_amount` | `6900.00` | Normalized Exact Match (numeric) |

Measured ALQari extraction scores are not asserted in this document.

## Table / Layout Evaluation

Layout and table tasks are not scored by text similarity. Practical evaluation dimensions:

- **Correct reading order** — content is returned in the order a human would read it (critical for right-to-left and multi-column pages).
- **Region detection** — paragraphs, headers, figures, and tables are located.
- **Table structure** — the table is recognized as rows and columns, not flattened text.
- **Row / column preservation** — cells map to the correct row and column.
- **Key–value relationships** — label/value pairs (e.g., "Total: 6900.00") are linked correctly.
- **Bounding-box agreement where applicable** — predicted regions overlap reference regions (e.g., using an overlap/IoU threshold).

Each dimension should be scored and reported separately rather than collapsed into one layout number.

## Arabic Handwriting

Arabic handwriting is a distinct task from printed OCR and must be scored separately. Factors that make it harder and that evaluation must account for:

- **Writer variation** — handwriting style differs greatly between writers.
- **Connected (cursive) script** — letters join, making segmentation ambiguous.
- **Low-quality scans** — forms are often photographed or scanned at low resolution.
- **Baseline differences** — handwritten lines drift, slant, and overlap.
- **Ambiguous characters** — visually similar letters are easily confused.
- **Diacritics** — inconsistent or partial tashkeel in handwriting.
- **Numeric fields** — handwritten digits (Arabic-Indic or Latin) in amounts and IDs.

**Printed and handwritten Arabic must not be merged into a single score.** Blending them hides where a system actually performs well and produces a number that is not comparable across datasets with different printed/handwritten ratios.

---

## Mixed Arabic / English

Many real documents mix scripts. Evaluation must handle:

- **Bidirectional (bidi) text** — right-to-left Arabic interleaved with left-to-right Latin.
- **English names** — proper nouns in Latin script.
- **IDs and invoice numbers** — alphanumeric tokens that must be transcribed exactly.
- **Dates** — multiple formats and digit scripts.
- **Amounts** — numeric values with currency and separators.
- **Arabic + Latin tokens** — words from both scripts in the same line.

For mixed documents, preserving **reading order** and **structured values** matters beyond raw text transcription: an ID or total that is individually correct but placed in the wrong field or wrong order is still a failure for downstream use.

## Latency & Throughput

Latency numbers are only comparable when measurement conditions are equal. Record the full context of every timing measurement:

- document / page size
- hardware (CPU/GPU, memory)
- model version
- batch size
- concurrency level
- preprocessing steps
- warm vs cold state (first request after start vs steady state)

Distinguish three separate quantities — do not conflate them:

| Metric | Definition |
|---|---|
| **Per-page latency** | Time to process a single page end to end |
| **Throughput** | Pages (or documents) processed per unit time under load |
| **Concurrency** | Number of requests processed in parallel |

Do not compare vendor-reported latency directly against measured latency unless the conditions (hardware, batch, concurrency, preprocessing, warm/cold) are equivalent.

---

## Reproducibility

Every benchmark run must record enough context for an independent party to repeat it:

- model / version
- date of the run
- configuration (parameters, prompts, options)
- preprocessing policy
- dataset version
- hardware / runtime environment
- metric implementation (the exact scoring code or tool and its version)
- random seeds where applicable

If a run cannot be reproduced from its recorded metadata, its numbers should not be published as a benchmark.

---

## Fair Competitor Comparison

When more than one system is compared, fairness rules apply:

- **Use the same inputs** — identical documents, ground truth, and preprocessing for every system.
- **Do not use a vendor's own benchmark numbers as direct proof against another system** — they were produced under different, undocumented conditions.
- **Distinguish vendor-reported from independently measured results** — label clearly which is which.
- **Do not interpret "not publicly documented" as "not supported"** — absence of documentation is not absence of capability.
- **Disclose prompts and configuration where possible** — so others can reproduce or challenge the result.

Comparisons describe measured outcomes under stated conditions; they do not make superiority claims or attack other systems.
